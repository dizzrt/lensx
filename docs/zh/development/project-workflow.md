# 项目工作流

## 事实来源

项目来源存在冲突时，采用以下顺序：

1. 当前源码和测试决定已经实现的行为；
2. 稳定 spec 决定已接受的能力需求；
3. 规范英文 docs 决定持续维护的架构和实现指南；
4. 活动 OpenSpec change 描述提议中或进行中的行为；
5. README 用于开发人员快速接入。

不要默默选择更方便的来源。应解决有意义的冲突，或者明确记录冲突。

## 文档治理

- `README.md` 是规范英文开发人员入口。
- `README-zh.md` 是其简体中文镜像。
- README 只包含介绍、环境要求、快速启动和贡献入口，不包含具体架构或实现设计。
- `AGENTS.md` 和 `openspec/config.yaml` 是英文 Agent 规则文件。
- `docs/en/` 包含规范实现与架构文档。
- `docs/zh/` 以相同相对路径镜像英文文档。
- `docs/AGENTS.md` 包含文档专用的 Agent 规则。

在同一个变更中更新两个语言版本。翻译必须保留相同的含义、范围、示例、限制和导航。

## OpenSpec 语言

- 活动 proposal、design、delta spec 和 task 产物使用 Agent 对话语言，除非用户另行指定。
- 活动产物在该语言下保持内部一致。
- `openspec/specs/` 下的主 spec 始终使用英文。
- 同步或归档 change 前，把将要进入主 spec 的需求翻译或改写为英文。
- 归档前同步稳定 spec。

## 变更生命周期

```text
explore
  -> propose
  -> 审查产物
  -> apply tasks
  -> validate
  -> 同步英文稳定 spec
  -> archive
```

- 探索阶段可以检查仓库并进行推理，但不实现应用代码。
- proposal 必须区分当前行为和提议行为，并说明非目标。
- design 在相关时记录架构、数据流、备选方案、风险和迁移。
- delta spec 定义规范行为和可观察场景。
- task 按依赖顺序排列，并且可以独立验证。
- 只有最终验证通过后，实现才算完成。

## Task 要求

每个 `tasks.md` 必须：

- 包含实现、测试和成对文档更新；
- 同时影响前端和 Rust 时明确列出两侧工作；
- 以最终验证章节结束；
- 包含前端测试、格式和静态检查、类型检查与生产构建；
- 包含 Rust 格式、测试和静态检查；
- 验证区域不受影响时说明理由，不能默默省略；
- 要求修复此次变更引入的 warning 和 error；
- 要求重新执行失败命令和完整最终验证集合。

## 临时材料

临时输入不是项目来源。它们可以辅助推理，但正式代码、测试、配置、docs、spec 和生成产物不能
链接、引用、导入或依赖这些输入。

临时示例包含有用信息时：

1. 对照当前仓库和已接受方向进行确认；
2. 将其改写为项目自身的需求、决策、示例或实现；
3. 移除所有临时来源信息和依赖；
4. 按正常流程验证生成的项目产物。

## 依赖变更

- 优先使用已有依赖和平台能力。
- 在考虑其他 UI 组件包前使用 Semi Design。
- 说明新依赖的必要性、备选方案、bundle 或运行时影响、维护责任和安全影响。
- 将重要依赖或组件库决策加入相关 OpenSpec design。

## 完成标准

在满足以下条件前，不要声称变更已经完成：

- 实现与已批准产物一致；
- 测试覆盖发生变化的行为；
- 英文 docs 与中文镜像一致；
- 必需的前端和 Rust 验证已经通过；
- 引入的 warning 和 error 已修复；
- 剩余限制已经明确报告。
