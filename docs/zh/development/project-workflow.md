# 项目工作流

## 事实来源

项目来源存在冲突时，采用以下顺序：

1. 当前源码和测试决定已经实现的行为；
2. 稳定 spec 决定已接受的能力需求；
3. 规范英文 docs 决定持续维护的架构和实现指南；
4. 活动 OpenSpec change 描述提议中或进行中的行为；
5. README 用于开发人员快速接入。

不要默默选择更方便的来源。应解决有意义的冲突，或者明确记录冲突。

在判断实现或工程约定前，先通过[文档索引](../index.md)阅读相关长期文档，并检索
[稳定规格](../../../openspec/specs/)。问题同时涉及实现与可观察契约时，两者都必须检查。
结合当前源码、测试和可执行配置确认事实；缺少、覆盖不足或互相冲突的证据必须明确报告，
不能用类似项目的经验代替。

按维护者明确选择，根目录的 `plugin-roadmap.md` 保留为历史规划。本次治理不处理其语言
同步；它不是同步维护的文档基准，也不是已交付行为的证据。

## 文档治理

- `README.md` 是规范英文开发人员入口。
- `README-zh.md` 是其简体中文镜像。
- README 只包含介绍、环境要求、快速启动和贡献入口，不包含具体架构或实现设计。
- `AGENTS.md` 和 `openspec/config.yaml` 是英文 Agent 规则文件。
- `docs/en/` 包含规范实现与架构文档。
- `docs/zh/` 以相同相对路径镜像英文文档。
- `docs/AGENTS.md` 包含文档专用的 Agent 规则。

语言策略值的唯一来源是 [govern-spec.yaml](../../../govern-spec.yaml)，
[根 Agent 指南](../../../AGENTS.md#language-and-mirroring)解释执行语义。
README 和 docs 列表中的首个语言分别是该文档面的语义基准。所有声明的翻译必须在同一任务中
严格同步，保留含义、范围、示例、限制与导航；缺失或过时的翻译不能延期处理。

`docs/` 下只允许直接放置 `AGENTS.md`，每个语言根目录下只允许直接放置 `index.md`。
其他长期文档进入已有主题分类。每个语言的根索引是唯一分类目录，主题 hub 仅引导对应分类
内的阅读。README、根 Agent 指南和驱动配置不能重复维护详细文档或功能目录。
README 导航指向对应语言索引及稳定规格入口；可保留解释相邻命令或高风险警告所需的上下文链接。

新增、移动或删除文档时，更新对应索引以及所有受影响的入站、出站链接，包括 docs 外部引用。
按最终路径验证链接，并保持语言树结构对应。根目录中持续维护的贡献指南或路线图同样遵守
docs 语言策略；历史材料不属于持续维护的基准。

## OpenSpec 语言

- 新增或实质改写 proposal、design、delta spec 和 task 正文时，根据根指南和
  `language_policy.active_changes` 当场解析语言。明确的产物语言要求优先；固定标签使用该语言，
  `auto` 使用当前任务的自然对话语言，不明确时参考相关现有产物，仍无法确定才提问。
- 代码、引文和工具输出不作为对话语言依据，也不能用驱动或稳定规格语言代替回退规则。
- 审计正文同样遵守该规则。保留未改动和已归档内容；仅更新复选框不触发翻译。
  保留机器使用的标题、schema 键、标识符、命令、路径和协议文本。
- 进入稳定规格的已接受内容必须翻译并整合为 `language_policy.stable_specs` 指定语言；
  源变更产物可以保留自身语言。
- 归档前同步稳定 spec。

## 变更生命周期

依次进行探索、提案、产物审查、任务实施、验证、稳定规格同步、治理与文档审计，以及同步结果
验证；另行获得归档指示后再归档。

- 探索阶段可以检查仓库并进行推理，但不实现应用代码。
- proposal 必须区分当前行为和提议行为，并说明非目标。
- design 在相关时记录架构、数据流、备选方案、风险和迁移。
- delta spec 定义规范行为和可观察场景。
- task 按依赖顺序排列，并且可以独立验证。
- 只有最终验证通过后，实现才算完成。

## Task 要求

每个 `tasks.md` 必须：

- 包含实现、测试和成对文档更新；
- 同时影响前端和 Rust 时明确列出两侧工作；
- 以最终验证与归档就绪章节结束，预留变更范围审计并记录下述项目级审计触发决定；
- 包含前端测试、格式和静态检查、类型检查与生产构建；
- 包含 Rust 格式、测试和静态检查；
- 验证区域不受影响时说明理由，不能默默省略；
- 要求修复此次变更引入的 warning 和 error；
- 要求重新执行失败命令和完整最终验证集合。

## 治理与归档就绪

在用户要求、治理面发生变化或发现漂移时协调项目治理。本流程本身不授权功能实现、归档、
暂存、提交、推送、发布或全局配置修改。保留工具拥有的集成文件，获准更新时使用所属生成器；
项目强制规则必须能脱离生成集成和已安装技能被发现。

### 必须执行的变更范围审计

每次归档都审查最终接受的变更产物、受影响的实现与测试、相关稳定规格、长期文档分类、索引、
声明的语言、链接和适用治理约束。修复变更引入或触及的不合规内容；触及的既有问题不能豁免。
实施阶段已做过的审计也要按最终接受范围重新确认，单独发起归档请求时同样如此。

将长期结论归入已有文档责任范围：架构与接口、业务或需求流程、关键约束与决策，以及相关的
可复用开发约定。任务已勾选、docs 树未变化或规格验证通过，都不能单独证明文档覆盖仍然有效。

### 有条件执行的项目级审计

变更影响下列治理面时，增加项目级审计：

- `govern-spec.yaml` 或根目录、目录内的 Agent 指南；
- README 语言版本或文档索引；
- 文档语言集合、目录结构或同步关系；
- 规格驱动的项目配置；
- 临时目录规则；
- 生成集成或其生成配置。

除直接文件修改外，还要考虑语义、组织和生成方式的变化。新增或删除文档并更新索引会触发；
仅编辑普通分类文档正文不会触发。审计前及修复后都要判断，修复也可能带来治理影响。

检查这些治理面的权威来源、导航、分类边界、语言一致性、临时路径和生命周期规则，不重新审计
全部产品实现或历史变更。没有治理影响的变更只需范围审计，并记录不触发项目级审计的理由。
无关既有问题留作后续事项，不暗中扩大范围；不能延期处理必需的范围内约束或失败检查来绕过就绪要求。

### 顺序与持久证据

归档前先将已接受 delta 同步为配置指定的稳定规格语言；没有适用 delta 时记录该结论。
随后完成变更范围审计和触发的项目级审计，同步受影响文档、索引、链接及声明语言，再验证同步
结果，最后才移动变更。范围内缺失、过时或未解决的文档与治理问题会阻止归档就绪。

新任务清单在最终验证与归档就绪组中预留这些工作；缺少证据的旧变更在归档前补充。
审计记录写入变更的 `tasks.md`，正文使用写入时解析的活动变更语言，完成后才能勾选。
每条记录包含：

| 证据 | 必需内容 |
| --- | --- |
| 审查范围 | 已接受产物及受影响的实现、测试路径或模块。 |
| 检查对象 | 相关规格、文档分类与具体路径、索引、语言、链接和治理约束。 |
| 项目级审计 | 触发决定及理由；触发时的额外范围、发现和修复。 |
| 结果与理由 | 已更新、无需更新或尚未就绪，并解释覆盖与合规结论。 |
| 更新路径 | 实际修改的规格、文档、索引、治理文件，或明确无修改及理由。 |
| 验证 | 实际命令或检查、结果及适用路径，包括同步、链接、语言一致性和规格验证。 |

无需更新也必须给出证据；计划执行的命令不算通过结果。流程保留在本文，审计事实保留在
`tasks.md`；聊天和 PR 摘要不能替代记录。就绪不等于执行或授权归档。获准移动变更后，再次
验证最终相对链接和已归档产物。

## 临时材料

项目根目录的 `.tmp/`、`.temp/`、`tmp/` 和 `temp/` 是被忽略的非权威输入。保持四个目录
均被忽略；发现已跟踪的临时文件时先报告，不能暗中取消跟踪。操作系统临时文件 API 不受影响。
临时输入可以辅助推理，但正式代码、测试、配置、docs、spec 和生成产物不能
链接、引用、导入或依赖这些输入。

临时示例包含有用信息时：

1. 对照当前仓库和已接受方向进行确认；
2. 将其改写为项目自身的需求、决策、示例或实现；
3. 移除所有临时来源信息和依赖；
4. 按正常流程验证生成的项目产物。

## 依赖变更

- 优先使用已有依赖和平台能力。
- 在考虑其他 UI 组件包前使用 Semi Design。
- 说明新依赖的必要性、备选方案、bundle 或运行时影响、维护责任和安全影响。
- 将重要依赖或组件库决策加入相关 OpenSpec design。

## 完成标准

在满足以下条件前，不要声称变更已经完成：

- 实现与已批准产物一致；
- 测试覆盖发生变化的行为；
- 英文 docs 与中文镜像一致；
- 必需的前端和 Rust 验证已经通过；
- 引入的 warning 和 error 已修复；
- 剩余限制已经明确报告。
