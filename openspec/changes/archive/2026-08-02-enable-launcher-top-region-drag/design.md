## Context

lensX 主窗口是透明、无装饰、不可缩放且始终置顶的 Tauri 2 窗口。当前 React App Shell 在 `home`、`search` 和 `page` 状态间复用统一顶部行：搜索状态显示 Semi Design `Input`，页面状态显示上下文栏与关闭按钮，最右侧始终是不可交互头像。窗口没有系统标题栏，当前代码也没有拖动区域或窗口拖动客户端，因此用户无法从这一视觉顶部区域移动窗口。

Tauri 的声明式拖动区域适合纯非交互标题栏，但对显式标记为拖动区域的输入元素会阻止默认鼠标行为。这个变化必须同时跨越 React 手势仲裁、Tauri 窗口权限、可测试边界、稳定规范和原生 macOS 验收。现有架构要求 React 拥有交互状态，Tauri/Rust 拥有原生窗口能力，并保持 `650px` 固定宽度与 `home=320px`、`search=480px`、`page=600px` 的离散高度不变。

## Goals / Non-Goals

**Goals:**

- 把从窗口上边缘到统一顶部槽下边缘的完整横向区域建模为 launcher 拖动区域，并覆盖搜索输入、页面上下文非操作区域、头像和空白。
- 让主鼠标按键的无移动单击继续完成输入框聚焦和光标定位，让按下后的移动由原生窗口拖动接管。
- 明确排除页面关闭按钮，并保持已有键盘、输入法、可访问性、主题和本地化行为。
- 通过可注入、类型化的前端 controller 调用 Tauri 原生拖动能力，并将权限限定到 `main` 窗口。
- 在自动化测试之外进行 macOS 原生拖动验收，验证 WebView 与原生窗口事件的真实交互。

**Non-Goals:**

- 不实现窗口缩放、最大化、最小化、吸附、位置持久化或额外标题栏按钮。
- 不改变 launcher 的尺寸状态机、快捷键、失焦隐藏和关闭转隐藏行为。
- 不为头像、顶部空白或页面上下文文字添加可访问操作语义。
- 不同时保留搜索框内的主鼠标拖选文字；发生手势冲突时窗口拖动优先，文本仍可通过单击和键盘选择。
- 不引入新的运行时依赖、组件库或用户可见文案。

## Decisions

### 1. 使用一个显式的统一顶部拖动容器

App Shell 将顶部内边距、顶部行以及其下方属于顶部带的间距收拢到一个明确容器，使命中区域与用户看到的完整顶部表面一致。该容器在 `home`、`search` 和 `page` 三种状态下保持同一职责，不根据查询内容或页面内容改变范围。

替代方案是只标记当前 `.launcher-top-row`。它无法覆盖视觉上属于顶部带的外侧内边距，用户仍会遇到看似可拖但实际不可拖的死区，因此不采用。

### 2. React 仲裁手势，Tauri 执行原生移动

顶部容器使用统一的主鼠标按下处理，通过事件委托判断来源：页面关闭按钮及未来显式标记的排除控件不触发拖动，其余位置调用类型化 `LauncherWindowDragController.startDragging()`。处理搜索输入时不主动阻止默认鼠标行为，使无移动单击仍能聚焦并定位光标；一旦指针移动，Tauri 的原生拖动循环移动窗口。controller 只暴露无参数、返回 `Promise<void>` 的能力，不向 React 暴露原生窗口对象、位置或尺寸。

桌面实现封装 Tauri 当前窗口的 `startDragging()`；浏览器与单元测试使用 inert 或 fake controller。React 只决定手势是否有资格发起拖动，Tauri capability 和原生运行时负责受限窗口操作。

替代方案一是把 `data-tauri-drag-region` 深度应用到整个子树。输入元素若被直接声明为拖动区域，Tauri 会阻止其默认鼠标行为；若不直接声明，输入又会阻止祖先拖动，无法同时满足需求。

替代方案二是新增一条仅代理 `start_dragging` 的自定义 Rust command。Tauri 已提供同等的受权限控制核心命令，额外代理不会增加校验信息或产品策略，只会形成重复边界，因此不采用。若原生验收证明 Tauri 核心 API 无法稳定维持输入单击行为，再将自定义 Rust 边界作为回退，而不改变 React controller 契约。

### 3. 明确区分可拖区域与可操作排除区域

页面上下文关闭按钮使用显式排除标记，事件处理沿目标到顶部容器检查排除祖先。排除发生在调用原生拖动之前，因此按钮的单击、键盘激活和焦点行为保持原样。头像虽然可以发起拖动，但仍保留 `aria-hidden`、不可聚焦且无按钮或菜单语义；拖动是窗口表面行为，不是头像产品操作。

只处理主鼠标按键。辅助按键、右键和键盘事件不发起拖动。双击不承担最大化语义，因为 launcher 是不可缩放、不可全屏的固定形状窗口。

### 4. 使用最小 Tauri 权限和可恢复失败

主窗口 capability 仅增加 `core:window:allow-start-dragging`，不增加位置设置、缩放、最大化或其他窗口变更权限。controller 拒绝时，App Shell 保持当前查询、选择、页面和焦点状态；开发环境记录可诊断错误，生产界面不显示新的技术错误文案，也不尝试用 JavaScript 手动更新窗口坐标。

### 5. 自动化覆盖契约，原生 smoke 覆盖真实拖动

前端测试通过 fake controller 验证顶部空白、输入、头像和页面上下文能发起拖动，关闭按钮及非主按键不会发起拖动，并回归输入聚焦、查询、键盘导航、输入法组合和页面关闭。配置测试验证最小权限只授予 `main` 窗口。由于 DOM 测试无法证明操作系统窗口实际移动，最终必须在固定原生 viewport 下完成 macOS smoke，并同时截图和检查计算样式以确认连续表面无视觉回退。

## Risks / Trade-offs

- [macOS 原生拖动循环可能吞掉 `mouseup` 或影响输入单击后的光标定位] → 使用不调用 `preventDefault` 的手势处理，并把搜索框单击、拖动、输入法和页面关闭列为阻断性的原生 smoke；如失败，在不改变 controller 契约的前提下调整事件阶段或切换到自定义 Rust 边界。
- [搜索框的鼠标拖选文字与拖窗使用同一手势] → 明确采用拖窗优先的产品取舍，保留单击定位、Shift 加方向键等键盘选择方式，并在规范中记录该边界。
- [未来顶部加入新按钮后意外触发拖动] → 采用显式可复用的排除标记，并测试排除元素及其图标子节点；新增顶部交互控件必须声明排除。
- [权限范围扩大] → 只授予 `core:window:allow-start-dragging`，capability 继续限定 `windows: ["main"]`，并以配置测试防止加入不相关权限。
- [仅浏览器测试产生虚假信心] → 将 macOS 原生移动与交互回归列为完成条件，浏览器/jsdom 只验证事件路由和 UI 状态。

## Migration Plan

1. 先增加类型化拖动 controller、桌面适配器和 fake/inert 实现，保持现有 App Shell 行为不变。
2. 向 `main` capability 增加最小拖动权限和配置检查。
3. 引入统一顶部拖动容器、排除标记和手势路由，并补齐自动化回归测试。
4. 更新英文文档及简体中文镜像，执行完整前端与 Rust 验证。
5. 在 macOS 原生窗口中完成三种展示状态的拖动、输入和关闭验收；验收失败则不完成 change。

回滚时移除顶部手势路由、桌面 controller 接线和新增权限即可；没有持久化数据、迁移文件或外部协议需要恢复。

## Open Questions

无待定产品决策。原生 smoke 可能要求调整事件阶段或 Tauri 适配方式，但不得改变本设计规定的可观察交互结果。
